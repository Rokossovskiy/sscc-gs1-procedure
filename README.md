# dbo.sp_GetNextGS1SSCC — выдача следующего SSCC (GS1)

Хранимая процедура MS SQL Server. Выдаёт следующий SSCC в формате `(00)` + 18 цифр.
SSCC строится из GS1-префикса компании `54602541`, 9-значного серийного номера и контрольной цифры GS1 Mod 10.
Серийный номер берётся из таблицы-счётчика, строку формирует существующая функция `dbo.fn_GenerateGS1SSCC`.

## Кратко

- **Принцип.** Счётчик двигается только вперёд. Пропуск номера допустим, повторная выдача — нет. Сплошной нумерации GS1 не требует.
- **Уникальность.** Один автофиксируемый `UPDATE ... WHERE Id = 1`: чтение, проверка границы и запись атомарны.
- **Внешняя транзакция.** Вызов внутри неё запрещён (50006): её откат вернул бы счётчик назад после выдачи SSCC.
- **Схема.** Инвариант «одна строка, значение 0..999 999 999» закрыт ограничениями `PRIMARY KEY`, `CHECK (Id = 1)` и `CHECK` диапазона.
- **Граница.** После 999 999 999 по умолчанию ошибка 50005 без записи в таблицу. Сброс на 0 только при `@AllowWrapAround = 1`.
- **Ошибки.** `THROW` с кодами 50001, 50002, 50004–50007, `@SSCC` остаётся `NULL`.
- **Выходной параметр.** `NVARCHAR(22)`: ровно `(00)` + 18 цифр, без хвостовых пробелов.

## Установка и вызов

Нужен SQL Server 2016 SP1 или новее (`CREATE OR ALTER`). В базе должны быть объекты из условия.
Скрипты не содержат `USE`, их выполняют в целевой базе в таком порядке:

1. `sql/dbo.tbl_SSCC_Counter_constraints.sql` — добавляет `Id`, PK и `CHECK`, текущее значение сохраняется. Если в таблице не ровно одна строка или значение вне диапазона, миграция останавливается и ничего не меняет.
2. `sql/dbo.sp_GetNextGS1SSCC.sql`.

```sql
DECLARE @SSCC NVARCHAR(22);
EXEC dbo.sp_GetNextGS1SSCC @SSCC = @SSCC OUTPUT;
SELECT @SSCC AS SSCC;  -- для серийного номера 1: (00)546025410000000016
```

Процедуру вызывают вне транзакции, до начала бизнес-операции. В режиме `IMPLICIT_TRANSACTIONS ON` вызов допустим, если транзакция ещё не открыта.

## Принятые решения

### Уникальность

```sql
UPDATE dbo.tbl_SSCC_Counter WITH (UPDLOCK, ROWLOCK)
SET @Serial = LastGS1SSCC = CASE WHEN LastGS1SSCC < @MaxSerial THEN LastGS1SSCC + 1 ELSE @MinSerial END
WHERE Id = @CounterId
  AND LastGS1SSCC >= @MinSerial
  AND (LastGS1SSCC < @MaxSerial OR (LastGS1SSCC = @MaxSerial AND @Wrap = 1));
```

Чтение, проверка границы и запись выполняет одна инструкция. Вторая сессия ждёт на блокировке строки и после фиксации первой видит уже новое значение.
Явной транзакции нет: `UPDATE` фиксируется сам и сразу отпускает строку, поэтому функция вызывается без блокировки.
`UPDLOCK` и `ROWLOCK` фиксируют намерение. Корректность обеспечивают атомарность `UPDATE` и PK по `Id`.
При `READ_COMMITTED_SNAPSHOT` решение тоже корректно: строки для изменения `UPDATE` читает с блокировкой, а не по версиям.

Почему не другие схемы:
- **`SELECT`, затем `UPDATE`** — две сессии прочитают одно значение.
- **`SELECT ... WITH (UPDLOCK)` для проверки границы, затем `UPDATE`** — корректно, но нужны явная транзакция и две инструкции. Условный `UPDATE` делает то же за одну.
- **`UPDATE ... OUTPUT inserted.LastGS1SSCC INTO @t`** — эквивалентно, но требует табличной переменной.

### Внешняя транзакция

Опасен не сбой, а успешный вызов внутри внешней транзакции, которая потом откатывается по бизнес-причинам.
SSCC уже вернулся вызывающему и, возможно, напечатан. Внешний `ROLLBACK` возвращает счётчик назад, и следующий вызов выдаёт тот же номер.
Внутренний `COMMIT` не помогает: он только уменьшает `@@TRANCOUNT`. Автономных транзакций в SQL Server нет.

Поэтому при `@@TRANCOUNT > 0` процедура завершается ошибкой 50006 до любых изменений. Проверка стоит до `SET XACT_ABORT ON`: судьбу своей транзакции определяет вызывающий.
Правильный порядок: получить SSCC, затем начать бизнес-транзакцию. Если она откатится, номер будет пропущен, но не выдан повторно.
`IMPLICIT_TRANSACTIONS` процедура отключает локально, иначе `UPDATE` открыл бы транзакцию у вызывающего. После выхода из процедуры настройка восстанавливается.

Если вызов внутри транзакций обязателен, нужен `SEQUENCE` (см. ниже): его значения выдаются вне транзакции и при откате не возвращаются.

### Схема

Инвариант «ровно одна строка» закрыт на уровне схемы: `Id TINYINT PRIMARY KEY` и `CHECK (Id = 1)`. Диапазон закрыт `CHECK (LastGS1SSCC BETWEEN 0 AND 999999999)`.
Повреждённое состояние нельзя записать. Сценарий «обновили все строки, потом откатили» невозможен, поэтому код 50003 больше не используется.
Ошибки 50001 и 50002 остались на случай удалённой строки или отключённого ограничения (`NOCHECK`).

### Граница счётчика

Верхняя граница вычисляется из длины серийного номера: `10^9 − 1`. Проверка стоит в `WHERE`, поэтому на границе без разрешения строка не обновляется и не блокируется на запись.
Причину отказа процедура выясняет отдельным чтением. Гонка между `UPDATE` и этим чтением может повлиять только на текст ошибки.
Сброс на 0 выполняется только при явном `@AllowWrapAround = 1`, `NULL` означает запрет. SSCC нельзя повторно использовать в течение года после отгрузки, а процедура не знает дат отгрузки. Поэтому решение о сбросе принимает вызывающий.

### Обработка ошибок

Стратегия — завершение с ошибкой: пустой результат легко пропустить, исключение остановит операцию явно. `@SSCC` присваивается последней инструкцией и при ошибке остаётся `NULL`.

| Код | State | Ситуация |
|---|---|---|
| 50006 | 1 | Вызов внутри транзакции |
| 50007 | 2, 3 | Неверные длины или префикс в константах процедуры |
| 50001 | 4 | Нет строки с `Id = 1` |
| 50002 | 5 | Значение вне 0..999 999 999 (ограничение отключено) |
| 50005 | 6 | Диапазон исчерпан, сброс не разрешён |
| 50004 | 7, 8 | Функция вернула `NULL` или строку неверного формата |

Проверки конфигурации и транзакции выполняются до `UPDATE` и номер не расходуют.
Если сбой произошёл после `UPDATE` (функция вернула мусор или упала), номер пропускается. Номер пропущенного серийного номера есть в тексте ошибок 50004.
Runtime-ошибки функции уходят вызывающему с исходным кодом.
TRY/CATCH не используется: явной транзакции нет и откатывать нечего.

### Семантика SSCC

- Ведущие нули сохраняются через `RIGHT(REPLICATE('0', 9) + номер, 9)`.
- Префикс хранится в `NVARCHAR(20)` и проверяется на ровно 8 ASCII-цифр. Неверная длина не усекается молча, а даёт ошибку 50007.
- Сумма длин префикса и номера проверяется на 17: иначе параметр функции `NVARCHAR(17)` молча усёк бы строку.
- Результат функции проверяется до присвоения: `DATALENGTH` учитывает хвостовые пробелы, `LIKE` в `Latin1_General_BIN2` проверяет `(00)`, переданные 17 цифр и одну ASCII-цифру.
- `NVARCHAR` выбран для согласованности с функцией. Данные чисто ASCII: при рефакторинге функций всю цепочку стоит перевести на `VARCHAR(22)`.
- Контрольную цифру процедура не пересчитывает: это ответственность существующей функции.

### Альтернатива: SEQUENCE

```sql
CREATE SEQUENCE dbo.seq_GS1SSCC_Serial AS BIGINT
    START WITH 1 MINVALUE 0 MAXVALUE 999999999 NO CYCLE CACHE 50;
-- в процедуре: SET @Serial = NEXT VALUE FOR dbo.seq_GS1SSCC_Serial;
```

Плюсы: значения не возвращаются при откате, поэтому вызов внутри транзакций безопасен. Сессии не блокируют друг друга.
Минусы: политика переполнения (`CYCLE` или `NO CYCLE`) задаётся в объекте, а не при вызове. При аварийном перезапуске теряется кэш, и появляются пропуски.
Табличный счётчик оставлен, потому что он уже есть в базе и позволяет выбирать политику при вызове. На `SEQUENCE` стоит перейти, если нужен вызов внутри транзакций или выдача SSCC станет узким местом. При миграции `START WITH` = `LastGS1SSCC + 1`.

## Допущения

- `LastGS1SSCC` хранит последний выданный серийный номер. При значении 0 первый вызов выдаёт номер 1.
- При `@AllowWrapAround = 1` после 999 999 999 выдаётся номер 0: `(00)546025410000000009`.
- Префикс `54602541` задан константой в процедуре, как указано в условии.

## Ограничения

- **Пропуски номеров.** Номер пропускается, если после `UPDATE` упала функция или внешняя бизнес-операция откатилась.
- **Повтор после сброса.** При `@AllowWrapAround = 1` вызывающий сам отвечает за то, что старые номера можно использовать повторно. Приближение к границе нужно мониторить.
- **Пропускная способность.** Вызовы проходят последовательно через одну строку, но блокировка держится только на время `UPDATE`.

## Замечание к условию

В примере из условия `(00)546025410000000017` контрольная цифра не соответствует GS1 Mod 10.
Для `54602541000000001`: цифры на нечётных позициях слева (вес 3) — 5 + 6 + 2 + 4 + 0 + 0 + 0 + 0 + 1 = 18, × 3 = 54. На чётных (вес 1) — 4 + 0 + 5 + 1 + 0 + 0 + 0 + 0 = 10.
Сумма 64, контрольная цифра (10 − 4) mod 10 = 6, SSCC `(00)546025410000000016`. На процедуру это не влияет: цифру вычисляет существующая функция.
