# dbo.sp_GetNextGS1SSCC — выдача следующего SSCC (GS1)

Хранимая процедура MS SQL Server. Она выдаёт следующий SSCC в формате `(00)` + 18 цифр.
SSCC строится из GS1-префикса компании `54602541`, 9-значного серийного номера и контрольной цифры GS1 Mod 10.
Серийный номер берётся из таблицы-счётчика, строку формирует существующая функция `dbo.fn_GenerateGS1SSCC`.

## Кратко

- **Уникальность.** Счётчик меняется атомарным `UPDATE` единственной строки `dbo.tbl_SSCC_Counter`. Блокировка строки держится до конца транзакции, поэтому параллельные вызовы выстраиваются в очередь.
- **Граница.** Серийный номер лежит в диапазоне 0..999 999 999. После 999 999 999 выдаётся 0.
- **Ошибки.** Процедура завершается с ошибкой: `THROW` с кодами 50001–50004. Транзакция откатывается, номер не расходуется, `@SSCC` остаётся `NULL`.
- **Выходной параметр.** `NVARCHAR(22)`: ровно `(00)` + 18 цифр, без хвостовых пробелов.
- **Проверка.** 15 автоматических проверок: граница счётчика, аномалии таблицы, сбой функции и конкурентный тест 8 × 250 вызовов.

## Установка и вызов

Нужен SQL Server 2016 SP1 или новее: процедура создаётся через `CREATE OR ALTER`. В базе должны быть объекты из условия: `dbo.tbl_SSCC_Counter`, `dbo.fn_GS1SSCC_CheckDigit` и `dbo.fn_GenerateGS1SSCC`. Скрипт не содержит `USE`, его нужно выполнять в целевой базе.

```sql
DECLARE @SSCC NVARCHAR(22);
EXEC dbo.sp_GetNextGS1SSCC @SSCC = @SSCC OUTPUT;
SELECT @SSCC AS SSCC;   -- для серийного номера 1: (00)546025410000000016
```

## Соответствие требованиям

| Требование | Реализация |
|---|---|
| Следующее значение счётчика | Один атомарный `UPDATE ... SET @Serial = LastGS1SSCC = <новое значение>` |
| 17-значная строка | Префикс-константа + `RIGHT(REPLICATE('0', 9) + номер, 9)`: ведущие нули сохраняются |
| Вызов `fn_GenerateGS1SSCC` | Результат проверяется до возврата: длина, префикс, переданные 17 цифр, контрольная цифра |
| Выходной параметр | `@SSCC NVARCHAR(22) OUTPUT` |
| Конкурентный доступ | Блокировка строки счётчика до конца транзакции; тест: 8 сессий × 250 вызовов |
| Граница 0..999 999 999 | После 999 999 999 выдаётся 0 |
| Точный тип без хвостовых пробелов | `NVARCHAR(22)` и проверка `DATALENGTH` результата функции |
| Обработка ошибок | `XACT_ABORT ON`, `TRY/CATCH`, `THROW` с кодами 50001–50004 |
| Без магических чисел | Префикс, длины, границы и коды ошибок вынесены в именованные переменные |

## Принятые решения

### Уникальность

Чтение, инкремент и получение нового значения выполняются одним оператором:

```sql
UPDATE dbo.tbl_SSCC_Counter
SET @Serial = LastGS1SSCC = CASE ... END;
```

Оператор берёт эксклюзивную блокировку строки и держит её до конца транзакции. Две сессии не могут получить одно значение: вторая ждёт фиксации первой и читает уже новое значение.

Почему не другие схемы:
- **`SELECT`, затем `UPDATE` без хинтов.** Две сессии прочитают одно значение и выдадут одинаковый номер.
- **`SELECT ... WITH (HOLDLOCK)`.** Обе сессии держат S-блокировку и пытаются перейти к X. Это классическая взаимоблокировка при конвертации.
- **`SELECT ... WITH (UPDLOCK, HOLDLOCK)` + `UPDATE`.** Корректно, но два оператора вместо одного.
- **`UPDATE ... OUTPUT inserted.LastGS1SSCC INTO @t`.** Эквивалентно по надёжности, но требует табличной переменной. Присваивание в переменной короче.

При включённом `READ_COMMITTED_SNAPSHOT` решение тоже корректно. `UPDATE` выбирает изменяемые строки блокирующим чтением с U-блокировкой, а не по версиям строк.

Цена решения в том, что все вызовы последовательно проходят через одну строку. Транзакция короткая: одно обновление и вызов скалярной функции. Для выдачи SSCC этого достаточно.

### Альтернатива: SEQUENCE

```sql
CREATE SEQUENCE dbo.seq_GS1SSCC_Serial AS BIGINT
    START WITH 1 MINVALUE 0 MAXVALUE 999999999 CYCLE CACHE 50;
-- в процедуре: SET @Serial = NEXT VALUE FOR dbo.seq_GS1SSCC_Serial;
```

Плюсы: сессии не блокируют друг друга, `CYCLE` даёт сброс на 0 без дополнительного кода.

Минусы: номер, выданный в откатившейся транзакции, теряется. При аварийном перезапуске теряется кэш, и появляются пропуски.

Табличный счётчик выбран, потому что он задан условием и при ошибке номер возвращается. На `SEQUENCE` стоит перейти, если выдача SSCC станет узким местом. При миграции `START WITH` = текущее `LastGS1SSCC + 1`.

### Граница счётчика

Верхняя граница вычисляется из длины серийного номера: `10^9 − 1`. После 999 999 999 счётчик становится 0, и этот номер выдаётся.

Недопустимое значение в таблице молча не исправляется. Оно остаётся как есть, а процедура завершается ошибкой 50002 с фактическим значением в тексте. Автоматическая «починка» скрыла бы повреждение данных и могла бы привести к повторной выдаче номеров.

### Обработка ошибок

Выбрана стратегия «завершение с ошибкой». Пустой результат легко пропустить в вызывающем коде, а исключение остановит операцию явно. Выходной параметр при этом тоже остаётся `NULL`: так защищены вызывающие, которые проверяют результат.

| Код | Ситуация |
|---|---|
| 50001 | В `dbo.tbl_SSCC_Counter` нет строки |
| 50002 | Значение счётчика вне диапазона 0..999 999 999 |
| 50003 | В таблице больше одной строки |
| 50004 | `fn_GenerateGS1SSCC` вернула `NULL` или строку неверного формата |

Все аномалии таблицы определяются по результату одного `UPDATE` (`@@ROWCOUNT` и полученное значение), без дополнительных запросов. Runtime-ошибки внутри функции передаются вызывающему в исходном виде через `THROW`.

При любой ошибке транзакция откатывается, поэтому номер не расходуется. Номер фиксируется только тогда, когда корректный SSCC сформирован.

### Семантика SSCC

- Ведущие нули серийного номера сохраняются через `RIGHT(REPLICATE('0', 9) + номер, 9)`.
- Выходной параметр имеет тип `NVARCHAR(22)`: это ровно `(00)` и 18 цифр. Тип Unicode, как у результата функции, поэтому неявного преобразования нет.
- Результат функции проверяется до присвоения. `DATALENGTH`, в отличие от `LEN`, учитывает хвостовые пробелы. `LIKE` проверяет `(00)`, переданные 17 цифр и наличие одной контрольной цифры. Поэтому усечение при присвоении исключено.
- Контрольную цифру процедура не пересчитывает. Это ответственность существующей функции, и повторный расчёт в процедуре означал бы дублирование логики.

## Допущения

- `LastGS1SSCC` хранит последний выданный серийный номер. На таблице со значением 0 первый вызов выдаёт номер 1.
- После 999 999 999 выдаётся номер 0. SSCC `(00)546025410000000009` формально корректен.
- Префикс `54602541` задан константой в процедуре, как указано в условии.

## Ограничения

- **Повтор номеров после сброса.** По правилам GS1 SSCC нельзя использовать повторно в течение года после отгрузки. В продакшене приближение к верхней границе нужно мониторить или заранее планировать расширение диапазона.
- **Внешняя транзакция.** Если процедуру вызвали внутри транзакции, при ошибке откатывается и она. С `XACT_ABORT ON` такая транзакция всё равно становится нефиксируемой.
- **Уровень изоляции SNAPSHOT.** Если вызывающий открыл транзакцию в `SNAPSHOT`, параллельный вызов может завершиться ошибкой 3960 (update conflict). Такой вызов нужно повторить или выполнять вне snapshot-транзакции. `READ COMMITTED` и RCSI работают корректно.
- **Пропускная способность.** Вызовы выполняются последовательно на одной строке, см. раздел про `SEQUENCE`.

## Замечание к условию

В примере из условия указано `(00)546025410000000017`. Контрольная цифра в нём не соответствует GS1 Mod 10.

Расчёт для `54602541000000001`:
- цифрам на нечётных позициях слева назначается вес 3, остальным — вес 1;
- сумма цифр с весом 3: 5 + 6 + 2 + 4 + 0 + 0 + 0 + 0 + 1 = 18, умножаем на 3 и получаем 54;
- сумма цифр с весом 1: 4 + 0 + 5 + 1 + 0 + 0 + 0 + 0 = 10;
- итог 64, контрольная цифра (10 − 4) mod 10 = 6.

Правильный SSCC: `(00)546025410000000016`. На процедуру это не влияет: контрольную цифру вычисляет существующая функция.

## Рекомендации к схеме (вне рамок задания)

Ограничение `CHECK (LastGS1SSCC BETWEEN 0 AND 999999999)` и ограничение «ровно одна строка» перенесли бы проверки целостности из процедуры в схему. Например, для второго подойдёт ключевой столбец `Id` с `CHECK (Id = 1)`. Тогда повреждённое состояние нельзя было бы даже записать.
